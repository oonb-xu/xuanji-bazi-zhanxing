## 1 这份数据为什么价值最高

用户提供的《命理全息档案：癸水建禄 · 自我剖析白皮书》**不是又一份原始数据，而是专家的完整断语**
（格局 / 五行权重 / 胎元 / 命宫 / 身宫 / 星盘逐项 / 事业 / 婚姻 / 事件）。
⇒ 它可以当**专家基准**，把本项目一直缺的「**实现正确性对照**」补上。

> **对拍纪律**：专家断语算「**另一套实现**」，不算「真理」。
> 一致 ⇒ 引擎实现正确；不一致 ⇒ **逐条查明**（可能是引擎真 bug，也可能是口径差）。

## 3 三项不一致的逐条诊断

### 3.1 🔴 命宫：**引擎真 bug**（ARCH-1 结案）

- 专家：**己酉**；引擎 `L4_mingGong`：**癸卯**
- **关键旁证**：本项目**锁定库** `data/records/bazi_meta_db.json` 的 `tai_ming_shen.minggong` **也是己酉** ——
  **即"库值是对的、引擎公式是错的"**（这份档案把这个悬案close了）。
- 另一处可疑：引擎算出的命宫 **癸卯 与胎元 癸卯 同值** —— 两个不同的推导却得到同一结果，本身是警号。
- 引擎现行规则串：`和≤14→14−和；和>14→26−和；0 取 12`，本盘 `sum=10 → 4 → 卯`。
  **要得到酉（序 9），该规则不成立** ⇒ 需重推（现已有**已知正确输出**可作拟合目标）。

### 3.2 九宫群星：**引擎数据缺口**（非 bug）

专家把 **凯龙星（Chiron）** 计入九宫群星；引擎天体表里**没有凯龙**。
⇒ 属**功能缺口**：需在 `computeNatal` 的 bodies 里补凯龙（`astronomy-engine` 无凯龙 → 需外部星历或近似算法）。

### 3.3 日月关系：**口径差（两种都合法）**

| 口径 | 判定 | 依据 |
|---|---|---|
| **整宫制**（专家） | **日月冲** | 太阳摩羯 vs 月亮巨蟹 = **对宫** ⇒ 星座层面即对冲 |
| **容许度制**（引擎，R-V6） | **非冲** | 黄经差 **161.7°**，离 180° 差 **18.3°**，超出容许度 |

**两者都不错，只是定义不同。** 此前本项目只实现了容许度制（R-V6），
**从未声明"整宫制"也是合法口径** ⇒ 属**口径未登记**，不是引擎算错。

## 4 本轮修掉的真 bug：**双系统调用未走真太阳时**

- 首版 CLI 直接 `compileBazi({ at: '2007-12-25 17:30' })`（**民用时**）→ 时柱 **辛酉**
- 正确路径：`baziClock({...})` → `at = '2007-12-25 16:26'`（真太阳时，偏移 **−63.6 分钟**）→ 时柱 **庚申** ✅ 与专家一致
- **根因**：R-T2 早已规定"中方侧计算一律用真太阳时"，但**没有任何机检约束"调用方必须走真太阳时"**，
  于是 CLI 里一个民用时调用就静默产出错误时柱（**又是"沉默的错"**）。

## 5 新增裁定

| 编号 | 裁定 |
|---|---|
| **R-G1** | **专家基准（Ground Truth）对拍**：专家断语算「另一套实现」不是真理；一致⇒实现正确，不一致⇒**逐条查明**后归入「引擎 bug / 数据缺口 / 口径差」三类之一，**禁止直接判"引擎错"** |
| **R-G2** | 八字排盘**必须经 `baziClock` 真太阳时**再调 `compileBazi`（R-T2 的调用级落实）；**直接传民用时视为违规** |
| **R-G3** | **ARCH-1 结案：命宫 = 己酉**（专家与锁定库一致）。引擎 `L4_mingGong` 现行公式产出 **癸卯** 为**错**，须重推；拟合目标已知（丁亥壬子癸巳庚申 → 己酉） |
| **R-G4** | 星盘「冲」有**两种合法口径**：**整宫制**（星座对宫）与**容许度制**（R-V6）；输出**必须并列标注**，不得单方面判"不一致" |
| **R-G5** | 引擎天体表缺 **凯龙星（Chiron）** —— 记为**数据缺口**待补（非 bug） |
| **R-G6** | 对拍脚本的**字段名与比对函数本身也要机检**：本轮 3 处假阴性（`ganZhi` vs `ganzhi`、`bz.mingGong` 不存在、严格字符串比对"建禄格（…）"）**全部由对拍自身暴露** |
