# 外部数据库接入 + 数据权重模型 · 规则冻结表 v1.0

实现：`src/cross/ingest.mjs`（接入与对拍）、`src/cross/weights.mjs`（权重模型）、`cli-db.mjs`（Part 1–8 全链条）。
触发场景：用户给出一份**手写的多体系数据库**（八字/星盘/紫微/胎命身/大运/神煞），要求按其推演并计算权重。

---

## 1 处理顺序（不可调换）

```
接入 → 对拍 → 权重 → Part1–4 → Part5 → Part6(+时间线) → 6.7 → Part8 → rule 库修正
```

**为什么先对拍再推演**：手写数据库里可能同时含有正确值、口径差异值与笔误。若直接采信，错误会顺着
Part5/6/8 一路传播；若直接覆盖，则丢失用户的有效先验。所以先出一张**逐条对拍表**，三类状态：

| 状态 | 含义 | 处理 |
|---|---|---|
| 一致 | 引擎复算与 DB 声称相同（或同向） | 采信，权重高 |
| **冲突** | 两者不可调和 | **不静默采信任一方**——列入报表，权重降到 0.35，等人工裁定 |
| 不可对拍 | 本引擎无该能力（紫微/大运评级/部分神煞） | 登记为「外部输入」，计低权，**不参与判定** |

## 2 归一化
- 天体：`sun/moon/ascendant/mercury…pluto` → 中文本命盘名；`nodes.north/south` → 北/南交点
- 相位：角度 → 名称（0 合相 / 60 六分相 / 90 四分相 / 120 三分相 / 150 梅花相 / 180 对冲）
- 四柱：`{stem,branch}` → `干支`字符串 → 交给 `compileBazi`

## 3 权重模型（用户要求「计算每个数据的权重」）

```
weight = 100 × S × E × C × I
trust  = 100 × S × E × C        （纯正确性，不含影响面）
```

| 因子 | 取值 | 来源 |
|---|---|---|
| **S 来源可信度** | 规则表 1.00 / 引擎严格（有唯一等式，可与库对拍）0.95 / 引擎启发（规则表未给、由裁定补全）0.70 / 外部输入 0.55 | `SOURCE_TIER` |
| **E 证据强度** | `(支持 + 1) / (支持 + 反例 + 2)`，无证据 = 0.50，3 支持 0 反例 = 0.80 | 映射库/知识库的同名 claims |
| **C 一致性** | 与引擎对拍 一致 1.00 / 冲突 0.35 / 不可对拍 0.75 | 对拍结果 |
| **I 影响面** | `0.80 + 0.20 × min(被依赖 Part 数 / 5, 1)` | `IMPACT_REFS` 静态依赖表 |

**两条刻意的设计选择（可能被挑战，故写明）**：
1. **I 乘进权重**：一条完全正确但无人引用的数据，对结论的价值低于一条正确且被多处依赖的数据。若只想要正确性，读 `trust` 列。
2. **零证据时封顶**：`E` 在没有库证据时恒为 0.50，因此**单张盘推不出「高」权项**（实测 56 条 → 高 0/中 29/低 27）。
   这是设计而非缺陷：权重应当随跨盘证据累积而上升；一旦某条 claim 在映射库拿到 3 盘支持，`E` 升到 0.80，权重随之抬升。

## 4 rule 库修正

- 每次推演都调 `runDbDiscovery()` → 新证据经 `observe()` 追加进 `rules`（`data/mapping-library.jsonl`），
  更新建议进 `proposal`（pending-human）。
- `--apply` 把**本命盘**的 pending 建议按「用户指令」批量采纳，每条写一条 `decision` 事件（可追溯、可回放）。
- 结论仍受 6.7 的门槛约束：`verified` 需 ≥3 张不同命盘且 0 反例。**采纳建议 ≠ 结论成立**。

## 5 实现裁定

| 编号 | 未定义处 | 裁定 |
|---|---|---|
| R-E1 | 权重公式 | 见 §3；变更必须同步改本节与本文件 §3 与 `weights.mjs` 头注释 |
| R-E2 | 「同向」如何判 | 强弱/格局这类分级用语，DB 与引擎措辞不同（如「身极旺」vs「身旺」）→ 按**语义同向**判一致，非遗字符串相等 |
| R-E3 | 用神多套怎么办 | DB 常给多套（调候/格局/通关），本引擎只出扶抑用神 → 引擎值落在 DB 任一套中即判一致 |
| R-E4 | 紫微段 | 本引擎**无紫微斗数模块**；一律「不可对拍」，只登记与计权，不参与任何判定，也不据此改 rule 库 |
| R-E5 | 大运评级 | DB 未给出生时刻时大运无法复算（承 R-D8）→ 不可对拍 |
| **R-B9** | **从强格判据修正** | 原 R-B4 只看印比占比 ≥0.80。**新增守卫**：还须「克泄耗**不透干**且**无本气之根**」。反例：癸巳日 印比占比 0.841，但丁火透干、巳本气为丙 → 判**身旺**而非从格。（中/余气之根不算，否则寅中丙火会否掉一切从旺格） |
| **R-B10** | 忌神取值修正 | 原实现 `pick()` 对忌神也取「最缺者」，语义错误。修正：**用神取最缺、忌神取最旺**。反例：癸盘忌神应为水（6.0）而非金（3.0） |

> R-B9 / R-B10 是**被一次真实推演逼出来的引擎缺陷**：对拍时 DB 的 `geju_boundary`（"非从格，因日支巳火有根，丁火透干"）
> 与 `jishen:[水,金]` 两条声明同时指向这两个 bug。这正是「先对拍」的价值。

## 7 已知未决

1. **权重公式的 I 因子**（影响面）是裁定值；若认为「权重应纯粹反映正确性」，去掉 I 即可（`trust` 列已经给出）。
2. **E 因子的证据来源**目前只接映射库的 claim 匹配（按前 6 字模糊匹配），未做严格的 claim 归一化 → 可能出现误配。
3. **紫微、部分神煞、大运评级**在本引擎无法复算，长期停留在「外部输入」档。
4. **`--apply` 是用户显式指令才启用**；默认仍走 pending-human 队列。
5. 对拍表里的「口径差异」（如本例火权重 3.0 vs 1.5）**不判为错**，但会让该条降权——若用户认为口径应以 DB 为准，需改 R-B1 而非改本条。
